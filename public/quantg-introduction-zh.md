## 前言

我个人在开发一个面向日本股票的 AI 量化系统「QuantG」，从数据获取、因子（用来选股的指标）挖掘、每天的买卖判断，到在模拟账户里验证，整个流程都能自动运行。

它的核心是**让 LLM 自己挖掘因子**。本文不讲细节实现，主要介绍这个系统是按什么思路搭起来的。

## 整体流程

```text
自动拉取数据
  ↓
时点一致的数据（只用当天能知道的信息）
  ↓
因子主题・因子定义 → LLM 编写因子代码
  ↓
自动评估与前向验证 → 因子池
  ↓
每天的买卖判断 → 模拟账户・历史回放
  ↑
定时任务让整个流程自动运转
```

## 核心：让 LLM 自己挖掘因子

以往的因子研究，是由人提出假设、写公式、再做验证。这种方式能尝试的数量有限，思路也容易受写的人的习惯影响。

QuantG 把角色分开：

- **人**：决定往哪个方向挖、什么样的因子算好因子
- **LLM**：编写因子代码
- **系统**：自动评估写出来的因子，决定是否保留

LLM 写出的候选因子先用过去的数据筛选，再在筛选时还没见过的区间里重新确认（前向验证）。两关都通过的才进入因子池，用于买卖判断。

挖掘规则本身也会不断改进。每隔一段时间，LLM 会读取之前的结果，提出“参数范围这样改是否更好”的建议。但是否采纳不由 LLM 决定，而由系统决定：系统按建议重现过去，只有明显优于现行规则时才作为新版本采用。LLM 不能直接改数据库，也不能决定是否通过。**LLM 负责提建议，判断交给系统**，这条界线在整个系统里都坚持。

## 因子主题与因子定义：让 LLM 用尽数据

如果只对 LLM 说“帮我做个好因子”，出来的大多是用价格和成交量的、彼此相似的因子。财务、业绩日程、投资者类别交易情况等手上的大量数据，往往都用不上。

所以我先把挖掘范围定义成两层的“研究地图”：

- **因子主题**：大的研究方向。比如“短周期价格行为”“波动与价格区间”“流动性与成交量”“相对强弱与市场状态”“财报与事件”“基本面与估值”等
- **因子定义**：主题下面的具体研究课题。用结构化的方式写清假设、允许使用的输入数据、要探索的维度，以及使用数据时的规则

下面是一个因子定义的例子（对实际定义做了简化）：

```json
{
  "主题": "短周期价格行为",
  "定义": "短周期收益状态",
  "假设": "极短期收益的方向、连续性和加速度，可能区分惯性延续与过度反应后的反转",
  "输入": ["日线日期", "股票代码", "复权收盘价"],
  "维度": ["累计收益", "方向一致性", "收益加速度", "短期反转"],
  "规则": [
    "不使用信号日之后的数据",
    "数据不足时保留缺失值，不用未来数据填补"
  ]
}
```

定义里不写公式，也不写代码。只写“想研究什么”和“能用到什么程度”，具体公式交给 LLM 去想。

只要让因子定义覆盖到数据的各个领域，LLM 的探索范围自然就会扩展到全部数据。每个定义独立挖掘，各自的规则做版本管理，所以某个定义效果不好，也不会影响其他定义。

另外，价格行为这类**快因子**按较短的间隔重新挖掘，财报、披露这类**慢因子**则在新的披露积累到一定数量后再重新挖掘。流程相同，只是切分的尺子不同。

## 不看未来的数据

回测最怕的是不知不觉用到了未来的信息。QuantG 每次都只用“当天能知道的信息”重新生成评估和判断所需的数据。财务数据从披露之时起才使用，事后订正的值也只从订正那天起才可见。上面因子定义里写“规则”也是出于同样的原因。

## 模拟账户与历史回放

因子看起来再好，实际交易也不一定能赚钱。所以最终的评价要看扣除手续费后的交易结果。

- **模拟账户**：每天用因子池里的因子训练模型，决定下一个交易日的买入候选、限价和数量，并把成交、手续费、交割、止损、到期平仓都记进账本。可以并列多个资金、每天买入只数、止损幅度不同的账户，比较不同方针的差异。
- **历史回放**：重现“如果从过去某个时间点开始，用现在的因子和现在的方针开一个模拟账户，会怎么样”，按过去的每一天逐日走一遍。每套配置都能选择使用哪些因子，所以可以一个一个地加因子，比较每个因子到底起了多大作用。回放中每一天也只用到当天为止的数据。

系统还会比较某个因子“加入时”和“去掉时”的交易净利润，确认它是否真的贡献了收益。

## 用定时任务实现自动化

日常运行由定时任务完成，不需要人手操作。

- **自动拉取数据**：配合交易所的数据更新，如果数据还没追上最新交易日，就去拉取增量；交易日历也会提前延长。
- **每天的买卖判断**：数据到齐后，为所有有效账户执行当天的判断和模拟交易。
- **因子持续挖掘**：出现新的可评估区间后，自动推进因子挖掘。
- 此外，清理不再需要的中间数据、因子体检等也做成了定时任务。

调度器被设计成一个“薄闹钟”：到点问业务一侧“现在要不要做”，要做就请它执行，然后记录结果，仅此而已。做不做的判断全在业务一侧，所以新增定时任务时不用改调度器。另外，像失败后的恢复这类需要人来判断的操作，不会自动执行。

## 技术构成

页面用 React，后端用 Python（FastAPI）和 PostgreSQL。LLM 通过兼容 OpenAI 的接口调用，模型可以在配置里切换。所有服务都在一台 Mac 里运行，外部无法访问。耗时的处理会把状态保存在数据库里，中途停下也能接着继续。

## 结语

QuantG 的思路概括起来就是：**人决定“往哪里挖”和“什么算好”，LLM 负责“挖”，系统负责“验证”**。

系统还在发展中，目前正根据验证结果重做各层。进展之后会再写文章介绍。
